# Plan V5：自 Plan V4.5 以来的完成情况与当前基线

日期：2026-09-18  
性质：**阶段总结**，不是新的重构立项或对未完成能力的承诺。  
承接：[Plan_V4.5](Plan_V4.5.md)。本文以当前 `dev` 分支（`ad8d682`）的已提交代码、优化记录与已留存的验收结论为准，覆盖 2026-09-17 至 2026-09-18 的后续工作。

---

## 1. 结论摘要

V4.5 之后，项目的重心从“重建可信数据与推荐底线”扩展到了“让这些能力以可用、可观察、可管理的产品形态被使用”。本轮完成了以下六项主要交付：

1. **前端整体优化**：会话终端、登录/账户、侧栏、推荐呈现、进度反馈和桌面/移动布局统一到新的交互与视觉基线；新增“硬件日报”作为与会话终端并列的内容模块。
2. **管理员工作区三页面**：`/admin` 已有数据看板、用户管理、数据管理三个区块，服务端独立执行管理员鉴权，不能通过隐藏或伪造前端入口绕过。
3. **硬件日报**：新增需登录访问的日报阅读面、后端安全抓取与数据库缓存；日报内容与推荐 Truth DB 严格隔离。
4. **类似 Claude Code CLI 的工作过程反馈**：任务执行期间显示阶段状态、耗时和由推理服务实测的实时输出 token，使用户能看到“正在工作”，但不展示或伪造模型隐藏推理过程。
5. **路由链路优化**：在正式检索与双 Agent 选择前增加短执行计划，区分单件、整机、介绍、模型推荐、追问与普通问答；同时加强指定型号、上下文继承和规则兜底。
6. **输出质量优化**：把模型对象与硬件对象分开，单件/介绍/整机走不同呈现与检索边界；保留证据与未知项，压缩重复、泛化的警告文案。

这些交付没有改变 V4.5 的可信性原则：数据库事实、证据校验、融合后的 CPU/GPU 门禁以及“未知不能写成确定”的约束仍是推荐主链路的承重部分。前端体验、日报和后台均不能替代 TruthVerifier 或把规格级草案包装成可购买的完整 SKU 清单。

## 3. 前端大优化：从功能页面到连续工作台

### 3.1 已完成的用户界面改造

- 统一会话终端、侧栏、登录弹层、账户信息弹层和推荐块的视觉层级，减少历史上分散的样式与冗余说明；核心页面继续沿用终端化、等宽信息与轻量状态色的设计语言。
- 会话页能在不同任务状态间保持可理解的反馈：提交、排队、模型调用、融合及完成阶段不再只依赖最终文本；切换会话时会清理旧任务的临时状态，避免前一会话的进度串到后一会话。
- 推荐呈现与请求范围对齐：单件硬件请求只展示该类别；整机请求保留 CPU/GPU 核心配对与必要的规格方向；介绍请求不再套用推荐模板。这样既降低页面噪声，也避免用户把非目标部件误读成推荐结果。
- 登录、登出、账户信息与角色跳转已经接入前端状态管理。管理员登录后进入 `/admin`；普通用户不应看到或访问管理员工作区。
- 关键新页面和会话终端均纳入桌面/移动端检查，包含无横向溢出、状态反馈、结果阅读和侧栏模块切换等场景。

### 3.2 硬件日报模块

“硬件日报”是本轮新增的独立阅读入口，而不是推荐 Agent 的一个工具：

- 侧栏现在在“会话终端”和“硬件日报”之间切换；保留会话上下文，返回终端时可恢复原会话。
- 后端 `GET /api/hardware-daily/latest` 要求登录。服务只接受预期的知乎专栏文章 URL、知乎图片 CDN 和指定作者/“显卡日报”标题，去除追踪参数与固定推广行，降低外部内容直接进入页面的风险。
- 新增 `hardware_daily_cache`（迁移 `0012_hardware_daily_cache`）。刷新采用 PostgreSQL advisory lock 防止并发重复抓取；外部接口短暂失败时只回退到最后一份结构有效的缓存，并在页面标注缓存状态；无安全缓存时返回明确的不可用状态。
- 页面展示期数、日期、赞同/评论、摘要正文、来源链接与“内容为搜索摘要”的边界提示。图片懒加载且使用 `no-referrer`；小屏隐藏缩略图以保持可读性。

它依赖服务端配置的知乎访问凭据和上游可用性；缓存内容不参与模型检索、证据校验或硬件推荐，也不等同于项目自行核验的事实数据。

## 4. 管理员工作区：三页完成，编辑能力仍按阶段收敛

入口为 `/admin`，左侧三个区块的选择状态写入 `section` 查询参数，因此刷新与浏览器前进/后退可恢复当前区块。所有接口经过 `require_admin`，权限控制在服务端，而不是仅在前端隐藏导航。

| 页面 | 已交付能力 | 明确边界 |
|---|---|---|
| 数据看板 | 记录并汇总网站请求的推理用量；展示全站累计、日期区间合计和按 `Asia/Shanghai` 自然日补零的趋势图 | 是“已记录用量”而不是供应商账单；没有 provider usage、流中断或 HTTP 失败时保留为未知，绝不按字符数/流块数估算 |
| 用户管理 | 用户名搜索、分页、敏感认证信息不返回前端；删除前必须输入用户名确认；禁止删除管理员及存在活跃任务的用户 | 删除会级联清理账号相关会话/任务，但既有 `agent_run` 依既有规则保留为匿名审计，不承诺抹除全部运行记录 |
| 数据管理（一期） | 统一目录查询、硬件/模型过滤、名称或稳定标识搜索、分页详情；可编辑 `catalog_entity` 的名称、生命周期、发布日期和是否可推荐，并记录前后值与并发冲突 | 规格、价格、证据及其他关联表仍为只读；这不是任意 SQL 写入或完整的在线数据库编辑器 |

数据看板对应的 `token_usage` 不保存提示词、密码或账户外键，只记录模型、输入/输出/总 token、时间与来源；用户、会话和任务删除不会反向扣减历史累计。用户删除及目录编辑分别写入 `admin_change`，并以事务、行锁/`updated_at` 约束避免过期覆盖。

在 2026-09-18 的部署排查中，真实数据库已升级到 `0011_admin_workspace`，但发现旧 Uvicorn 进程仍可能继续提供不含新路由的 OpenAPI，从而使三个页面返回 404。该问题的正确处置是维护窗口内备份、确认无活跃任务、停止旧进程并启动单一新 worker，再核验管理接口；源码提交或完成迁移本身不等于运行中进程已热加载新路由。

## 5. 可观察的“思考过程”：展示工作态，不暴露思维链

本轮把原先较静态的 Thinking/Loading 提示改为更接近 Claude Code CLI 的过程体验，例如 `Cooking`、`Ruminating` 等工作态，加上任务耗时和实时 token 增长。其目标是让用户判断任务是否仍在进行、是否进入较长的检索/融合阶段，而不是向用户声称看到了模型的逐字推理。

实现边界如下：

- Query Job 通过已有 OpenAI-compatible `complete_chat` 网关请求流式 SSE；文本片段和工具参数片段在后端重组为原有的完整 `LLMCallResult`，不会破坏下游 schema、聊天或 Agent 调用约定。
- 仅接受推理提供方实际返回的中间 `usage.completion_tokens` 或 llama.cpp `timings.predicted_n`。prompt token、最终答案字数、字符数、chunk 数和本地估算都不会伪装成实时输出 token。
- 后端通过 `llm_usage` 事件为每个模型调用携带独立 `call_id` 与累计输出量，至多每秒两次；完成、取消或失败会用 `llm_usage_finished` 清除该调用。前端显示的是**当前仍在生成的调用之和**，并非整项任务的总 token，因此在调用切换时可以下降或消失。
- 真实联调已确认两个 llama.cpp endpoint 能返回中间 `timings.predicted_n` 与最终 usage；浏览器实测过从 1 增长到 26 token、融合结束后状态条撤下。短调用可能只显示极短的一次数值，这是采样和真实完成速度的结果，而不是补造动画。

完整口径、开关和异常回退见 [实时 token 用量说明](../Optimization/live-token-usage.md)；联调范围与未通过的历史 E2E 契约见 [路由与流式联调报告](../Optimization/routing-stream-validation-2026-09-17.md)。

## 6. 路由链路优化：先确定任务，再进入合适的事实路径

### 6.1 新增请求局部执行计划

自动模式现在先读取同一对话的有效需求，再由 agent-b 生成受限的短计划（最大 320 tokens）。计划只描述任务类型、单件/整机范围、CPU/GPU 或模型目标、用途、性能偏好、介绍对象、是否需要数据库及是否延续需求；它不生成产品事实或 SQL。随后该计划被传入检索、两路模型选择、真值核验、融合和展示环节。

计划加入了 `hardware / ai_model / general` 领域、`model` 目标角色和 `local_ai` 工作负载；分类使用 `temperature=0` 降低抖动。规则层仍优先于分类结果：明确的整机配置不能被模型降级成闲聊或单件问题；超时、格式错误或没有可靠历史锚点时保守转入核验，不凭空继承上一轮需求。

### 6.2 已解决的关键误路由

- 新完整推荐覆盖旧型号与旧范围；只有用户明确说“给这张显卡配主机”时，才把上轮**已核验**显卡绑定为指定部件。
- 单件 CPU/GPU、普通游戏整机、整机追问与产品介绍具有不同候选与展示范围；准确型号匹配区分 RTX 5070/5070 Ti、5090/5090D、14700K/14700KF 等边界，避免宽松 SQL 把相邻型号混入。
- “本地部署量化模型，推荐一个”不再被误解成处理器或整机：模型候选限定为 `ai_model`，硬件资源只作为筛选条件。相反，明确“购买显卡部署模型”仍以显卡为购买对象。
- “介绍”走本地目录和规格证据的专用读取路径，不进入双 Agent 推荐模板；“不要查数据库”等明确退出语句、概念解释和失败检索后的需求延续也已补齐回归覆盖。

请求完成事件保存原始模型分类与规则修正后的结论，便于定位“模型判断”与“确定性保护”之间的差异，同时不把提示词、SQL 或隐私内容暴露到前端。

## 7. 输出质量与上下文预算优化

### 7.1 面向用户的输出改进

- **范围正确**：单件请求不再附带无关整机清单；整机仍受原有 CPU/GPU 配对门禁约束；不再把新请求错误地与旧高端方案拼接。
- **对象正确**：模型推荐、硬件购买与“用现有硬件部署模型”分离。指定型号、量化档及资源条件无匹配时，会说明缺口，不自动放宽或换成另一类硬件。
- **资料表达更诚实**：产品介绍同时区分“已核验证据支持的字段”和“目录已收录、待补证据的字段”。名称证据不能冒充显存、功耗或其他规格证据；没有资料不等于产品不存在。
- **文案更紧凑**：删除每个字段、每条理由中重复的泛化免责声明，保留真正影响决策的前提、来源和余量。原始历史记录不被改写，折叠细节仍保留核验状态。

### 7.2 上下文与生成预算

系统会读取当前 llama.cpp endpoint 的 `/props.default_generation_settings.n_ctx`，按端点和模型 ID 缓存，而非把配置上限当成实际窗口。历史裁剪、压缩阈值和最终生成上限统一使用这一实际窗口；探测失败时才保守回退至设置值。

Agent 预检会先用 `/apply-template`（含工具定义与模板参数）渲染消息，再用 `/tokenize` 计数；两个步骤均成功才使用精确值。离线回退统一为 UTF-8 字节数的保守估算，明确不是实测 token，也不会进入实时 token 展示。真实验证中，agent-a 的模板计数 151、agent-b 为 271，均与服务端返回的 `prompt_tokens` 一致。

上述改动减少了上下文错配、无效检索与末端冗长生成，但不应被解读为所有复杂请求均已获得性能保证。历史的单次耗时样本只用于功能验收；当前尚未完成覆盖冷/热态、并发和 P95 的完整性能基准。

详情见 [单件推荐与介绍验收](../Optimization/intent-optimization-validation-2026-09-17.md)、[模型意图与产品资料优化](../Optimization/model-intent-and-product-evidence-2026-09-17.md)及[上下文窗口同步与文案精简](../Optimization/context-window-and-copy-2026-09-17.md)。

## 8. 验证状态

本轮有针对性的真实 HTTP、真实推理服务和浏览器验收，且没有改写 Truth 数据来获得通过。已记录的覆盖包括：管理员桌面/移动端、账户隔离、会话终端、单件/整机/介绍/模型目标纠偏、流式 token 显示、指定型号边界、日报模块以及桌面/移动端无横向溢出。

报告中出现的通过数对应各自的提交时点和测试集合，不能简单相加或当成“全站永久全绿”。尤其是 2026-09-17 的扩展桌面/手机 E2E 曾有 8 项历史页面契约失败，涉及能力标签、办公草案标题、部分核验提示和缺 GPU 的说明；这些断言没有通过删除来掩盖。因此当前准确表述是：**新增能力及其针对性回归已验证；全量跨场景 E2E 仍须在统一基线下继续收敛。**

可复核的证据与命令保存在各优化报告和被 Git 忽略的 `.local-logs/` 中；敏感登录 token 不提交仓库。

## 9. 仍未完成、不可被 V5 掩盖的事项

1. **推荐数据与整机边界**：实时价格、总价最优化、具体内存/存储/主板/机箱/散热 SKU、完整物理兼容、噪声和具体游戏帧率实测仍未完成。输出仍应称为已核验部件与规格方向的方案，而非完整可采购 BOM。
2. **复杂自然语言约束**：通用否定、跨轮多条件修改、任意长会话和所有硬件型号尚未完成全面评测；现有规则覆盖明确场景，不是自然语言约束求解器。
3. **管理员编辑闭环**：一期仅编辑安全白名单字段。规格、价格、Evidence、来源、关系、多值字段、发布包差异预览、审核和回滚尚未形成完整在线编辑闭环，不能开放任意表或任意 SQL 写入。
4. **管理员部署确认**：迁移文件已具备，但旧常驻后端必须在受控维护窗口重启；上线前仍须核验单 worker、OpenAPI 三个管理接口及用量回填窗口。
5. **日报依赖**：日报受外部凭据、上游搜索接口和缓存有效性影响；它只是受控展示的外部摘要，不是新闻事实核验、爬虫平台或推荐数据源。
6. **性能结论**：路由和上下文改动消除了已定位的慢路径，但尚无当前版本的 p50/P95、失败率、冷/热态和并发报告；不得用一两次实机回放宣称整体性能指标。

## 10. 后续工作顺序

建议继续遵循 V4.5 已定义的门禁，而不是立即扩大功能面：

1. 在统一环境复跑并收敛全量 E2E，先处理历史契约与当前产品边界不一致的失败项。
2. 对管理员工作区完成受控部署验证，确认新版进程、迁移和三项管理员 API 同时生效。
3. 建立固定评测题集，分别量化路由正确性、事实安全、范围正确性、输出边界与端到端延迟。
4. 根据评测的失败归因补充高影响数据和兼容规则；新增数据继续遵守发布包、Evidence、审核、dry-run 与可回滚流程。
5. 如确有长期后台编辑需求，再按“实体/规格表单 → 服务端事务 → 校验与审计 → 发布闭环”逐阶段扩展，不能将数据库管理权限直接暴露给浏览器。

V5 的定位是把当前成果与边界固定下来：产品体验已经显著向前推进，但推荐系统的可信性仍应优先于“看起来完整”的结论。
