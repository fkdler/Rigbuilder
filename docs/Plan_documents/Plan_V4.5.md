## 1. 执行摘要

RigBuilder 是一个面向个人电脑配置和本地 AI 部署的可解释推荐系统。当前架构为设备 A 运行 Vue/FastAPI/PostgreSQL，设备 B 运行两个 `llama-server` 推理实例；推荐过程只能从 `agent_catalog` 只读查询面取得候选，具体断言须经过同实体、`accepted` Evidence 的 `TruthVerifier` 核验。

本阶段已经完成三类基础能力：

1. **数据真值链重建**：审核、补充、导入了 v3-5 至 v3-10 发布包，扩充硬件、模型、变体、运行时支持、性能来源、别名与搭配策略；已恢复每条 Evidence 的真实采集时间，禁止再用发布日统一覆盖。
2. **推荐质量防线**：区分规格位置、第三方聚合指标与人工锚定政策；把 CPU/GPU 搭配门禁放在融合后，避免“高端显卡 + 入门 CPU”被包装成完整游戏整机；输出仍明确区分已核验部件、规格档位与待确认项。
3. **速度路径收敛**：`44decd0` 以任务聚焦、短上下文、早收敛、短选择、短理由、查询裁剪和 HTTP 复用，消除了大量无效 LLM 往返；历史受控样本的核心整机请求约 6.7–9.0 秒，但这不是 P95、也不是现版本质量提升的证明。

当前数据库终态（本轮本机检查）：652 个实体、2,132 条 Evidence、35 张 `truth` 表、16 个 `agent_catalog` 视图、10 张 `public` 表；后端全量回归为 **371 passed、6 skipped、0 failed**。真实采集时间分布为 2026-09-07：792、09-14：510、09-15：702、09-16：128；空值为 0。数据库备份 `D:\RigBuilder\.local-logs\backups\rigbuilder-20260916-213521.dump` 位于时间恢复之前，可用于该次数据变更回退。

最重要的未完成项不是继续堆数据或继续压 token，而是：重启设备 A 后端，先以固定题集做 HTTP + 真实 LLM + 前端端到端验收；基础账户、身份、会话归属与授权现已实施并验证；刷新轮换、注册/任务限流、持久审计和完整管理仍缺，**不能把 U0–U4 描述为全部完成**。

## 3. 系统边界与当前架构

### 3.1 双设备、双 Agent 拓扑

| 位置 | 运行内容 | 现状 |
|---|---|---|
| 设备 A | PostgreSQL `5432`、FastAPI `8000`、Vite `5173` | 新代码需手动重启后端才进入当前服务进程 |
| 设备 B `<DEVICE_B_IP>` | `llama-server` `8081`（agent-a）与 `8082`（agent-b） | 固定两个实例；不恢复三 Agent 架构 |

主链路：用户问题 → 路由 FAST/VERIFIED → 两个 Agent 只读 SQL → 证据绑定与 `decision_context` → 模型选择 → `TruthVerifier` → 融合/场景门禁 → 配置草案与理由 → Job/SSE 展示。

`TruthVerifier` 是不可削弱的承重约束：它能验证“模型是否把已查到的同实体事实抄对”，不能独立判定“这是否真的满足用户的游戏、预算、噪声或兼容需求”。因此，数据库正确、断言正确、配置适配、整机兼容和用户满意是五个不同层次，不能合并表述。

### 3.2 三层数据边界

| 层 | 职责 | 当前关键对象 | 不可跨越的边界 |
|---|---|---|---|
| `truth` | 实体、规格、来源、Evidence、发布、性能记录和规则的权威存储 | `catalog_entity`、规格表、`evidence_claim`、`performance_anchor`、`balance_rule` | 只能经审核后的发布包导入，不让模型直接写入 |
| `agent_catalog` | 模型唯一可见的只读查询面 | CPU/GPU/模型/变体、证据、排行、规则、别名、运行时视图 | 视图列须有正确的 Evidence 字段绑定；模型不能查询 `truth` |
| `public` | 会话、Job、事件、Agent 运行和审计 | `conversation`、`query_job`、`query_event`、`tool_call` | 现已增加用户归属和鉴权，完整安全运维与管理验收仍未完成 |

硬件 CPU/GPU 为型号级 `product`；内存、存储、电源和平台当前是需求/规格档位 `spec_profile`，不是可直接采购的具体 SKU。这是现阶段范围选择，不应在输出中伪装为完整 BOM。

| 待处理包直接导入会有枚举、字段键、依赖和重复实体错误 | 可产生错误实体或破坏契约 | 扩充合法枚举、重映射 141 条字段键、丢弃重复 workload 证据、纠正脏组织键、迁移 legacy 而非重复导入 | 所有新增发布均走 validate-only → dry-run → apply；不得将“已导入”推导为“全部来源正确” |

### 4.2 采集时间的现行规则

1. `collected_at` 记录事实/来源的实际采集或访问时刻，不是发布包 apply 时间，不是产品发布日期，也不是文档编写日期。
2. 新 bundle 有 Evidence 自带有效采集时间时使用它；没有时使用对应 `source_document.accessed_at`；没有可靠来源时不造时间。
3. 历史修复由 `backend/scripts/apply_field_and_timestamp.py` 按 manifest、哈希、来源和 Evidence ID 重放；正常导入由 `backend/scripts/import_v3.py` 自动完成缺省回落。
4. 时间、产品发布日期、价格观测时间、benchmark 测试日期必须在输出与计算中分别表达；任何一个缺失都不能用另一个代替。

### 4.3 仍然诚实保留的缺口

- `catalog_entity.release_date` 仍有 512 个空值；CPU `max_power_w` 146 个空、PCIe 代际 66 个空；GPU 带宽 31 个空、板卡功耗 22 个空。
- 笔记本 BGA CPU 的 socket 空值不是错误；无插槽时硬填插槽即造假。
- TechPowerUp、PCPartPicker 等受 robots/许可限制；Wikipedia 试采结果发生表头错配，未采纳。未知维持 NULL 优先于猜测。
- PassMark 未找到的其他可疑 SKU（如 `Ryzen 7 7700X3D`、若干 H/F/KF 命名）尚未获得用户确认，不得直接删除或断言不存在。

## 6. 性能、生态位与搭配政策

### 6.1 三种“排名”必须分开

| 名称 | 来源与含义 | 可以说什么 | 不可以说什么 |
|---|---|---|---|
| `position` 的规格位置 | 本库、同品类同架构的已核验规格分布 | 某字段在该有限样本中的相对位置 | 性能、市场档次、游戏帧率 |
| `performance_metric` / `performance_ranking.score` | PassMark 第三方聚合数据与其名次 | 来源公开的分数、名次、总体/同形态百分位 | 本项目实测、具体游戏表现 |
| `index_100` / `tier_label` | 19 个 `performance_anchor` 的版本化人工锚定插值 | 本项目当前产品政策下的相对生态位、搭配门槛输入 | 发布方百分位、市场真值、实测成绩 |

`index_100` 采用人工锚定是因为两种百分位方案均已失败：库内高端 CPU 样本会把 i5-12400 错判到低位；发布方全总体掺入大量旧件与核显，会把 RTX 3050 错判为旗舰。现行锚点示例为 i3-12100=26、i5-12400≈40、RTX 4060≈48、RTX 5090≈97。锚点是产品政策，应有版本、理由、变更评测和回滚，不可改名为“客观百分位”。

### 6.2 数据层与查询层

性能来源记录仍保留在 `benchmark_protocol → benchmark_run → benchmark_subject → benchmark_metric → metric_definition`；它们是来源、协议和数值的可追溯记录，并非本项目运行的 benchmark。当前有 244 个 run、969 条 metric、7 个 metric definition、2 个 protocol。`performance_metric` 提供来源、环境和原始指标，`performance_ranking` 提供排行派生值与锚定指数，二者的查询面语义已在 Prompt、表描述、DecisionContext 和 JSON schema 同步。

`entity_alias` 解决来源名与库内 canonical name 的连接问题，例如 PassMark 名称与库内名称或模型仓库名的差异。别名不携带 Evidence，也不允许模型据此生造规格。

### 6.3 `balance_rule` 与游戏门禁

九条规则是 v1 产品政策：office、general、gaming-1080p、gaming-1440p、gaming-4k、esports、local-llm、rendering、video。它们定义 CPU/GPU 最低指数、GPU/CPU 比例、是否必须独显和瓶颈方向。例如：

| 场景 | CPU 最低 | GPU 最低 | GPU/CPU 带宽 | 说明 |
|---|---:|---:|---|---|
| gaming-1080p | 40 | 40 | 0.8–2.0 | 双方均需达到基础门槛 |
| gaming-1440p | 45 | 55 | 1.0–2.6 | GPU 权重提高 |
| gaming-4k | 45 | 70 | 1.0–3.2 | 顶尖/顶级/旗舰/极致且未指明分辨率时的现行保守路由 |
| esports | 55 | 40 | 0.6–1.5 | 高刷更偏 CPU |
| local-llm | 20 | 55 | 不设比例 | 显存/带宽而非 CPU/GPU 比值才是关键约束 |

融合后 `request_scope.py` 会对已核验候选重新寻找通过规则的 CPU/GPU 配对，而不是只确保“有一个 CPU 和一个 GPU”。若指定“顶尖游戏”但候选池没有合格 `gaming-4k` 组合，系统只可输出已核验的部分方案并说明缺口，不能把失衡配对称为完整配置。此门禁直接修复了真实反例中 Radeon RX 9070 XT + Core i3-12100 被写成“顶尖游戏配置”的问题：i3 指数 26 不达 CPU 门槛，RX 9070 XT 指数 60.8 也不达该规则 GPU 门槛。

这只能防止已知的搭配失衡，不能证明“顶尖”必然适合每个游戏：规则未以帧率、1% low、预算、具体游戏或真实整机测试校准，且性能硬件来源目前仍是 PassMark 单一 tier-C 来源。

## 7. 推荐质量、会话和输出防线

### 7.1 已实现的质量改造

| 问题 | 已落地防线 |
|---|---|
| 单独要显卡却返回 CPU；整机结果缺 GPU | 请求类别硬门槛、CPU/GPU 独立选择槽、融合后核心角色覆盖 |
| 普通办公默认挑高功耗旗舰 | `office-fit-v1` 在事实核验后进行确定性场景排序；它是政策，不是办公实测 |
| 历史候选压过最新请求 | 历史仅投影身份和少量已核验事实；最新问题优先 |
| 模型未返回 UUID 或 Evidence 过多导致候选被裁成一行 | 只对本轮白名单视图返回的 key 补回 ID；行、Evidence 与 binding 联合裁剪 |
| 核显、性能、时间或资料缺失仍被写成确定事实 | Prompt、表描述、DecisionContext、断言校验和确定性模板均显式保留 unknown |
| 解释追问重新推荐或混入旧话题 | `answer_purpose=explanation` 锁定上一轮已选 CPU/GPU，重新核验事实但不重新排序；显式新约束才进入新决策 |
| 游戏整机使用入门 CPU 搭高端 GPU | 融合后游戏配对门禁；找不到有效组合时降级为部分方案 |

配置输出始终按 CPU、显示方案、主板平台、内存、存储、电源、散热、机箱逐项表达。具体型号缺失时只能给规格方向并标记待确认；电源只在 CPU/GPU 功耗证据均可用时估算，机箱、散热、主板 BIOS、视频输出和接口兼容没有证据时不得称为“已验证可购买整机”。

### 7.2 已知的质量边界

1. 自由中文仍无法做到对每个隐含因果、比较、性能承诺的形式化证明；当前有结构化 TruthVerifier、数字/名称检查、一次受控重写与确定性回退。
2. 游戏、预算、分辨率、刷新率、现有硬件、噪声与体积未被结构化收集时，系统必须询问或明确假设，不能把“顶尖”自动等价于单一采购清单。
3. 组件档位不是主板/内存/散热器/机箱的 SKU 兼容性数据库；`compatibility_edge` 仍为空。
4. 长对话、复杂否定、多次改预算、跨客户端并发仍未形成通用语义记忆方案。当前解释连续性是受限规则，不应超出其范围。

## 8. `44decd0` 速度优化：原因、证据与限制

### 8.1 为什么它显著变快

`44decd0` 并非主要靠更换模型或提高硬件参数，而是减少了推理路径中不产生新证据的 token 和回合。核心改动如下：

| 层 | 具体改变 | 为什么减少耗时 |
|---|---|---|
| 发现 Prompt | 普通 CPU/GPU 路径只暴露任务相关视图、字段与规则 | 大幅缩短 prefill；历史记录中 GPU Prompt 约 1,992 字符、整机约 2,245 字符，相比完整协议约 17,327 字符 |
| 上下文 | 历史 Fusion 结果投影为少量身份/事实，不重复塞入原 JSON、trace 和候选 | 避免长上下文重复预填；历史示例从约 8,777/10,776 字符降到 562/396 字符 |
| 查询 | 普通发现 SQL 顶层 `LIMIT 5`；拒绝重复 SQL；返回行、Evidence、binding 同步裁剪 | 减少数据库结果、证据序列化和模型阅读量，且不让 CPU 证据挤掉 GPU |
| 收敛 | 每个目标角色已有至少一个有事实证据的候选即可停止发现 | 不再为了凑备选数量重复调用模型；仍保留完整协议给价格、预算、测量和确认约束问题 |
| 选择 | 小模型只做“从已核验行中选 ID + 简短理由”的结构化选择，后端绑定身份与 Claims | 消除模型重写 UUID、事实 Claim、复杂 Recommendation JSON 失败后的重试 |
| 输出 | 短 Narrator、最多一次受控重写、失败即确定性模板 | 减少末端长生成；模板不会改动排序或证据 |
| 连接 | 复用 HTTP client/TLS context | 避免每轮重新建连接及证书读取开销 |
| 观测 | 关联 request 的分段计时 | 可分开观测队列、prefill/decode、工具、校验、narrator 和持久化，避免把所有慢都误归因于 GPU |

剩余瓶颈常是 decode，而非显存是否“还剩很多”。两个模型共享同一 GPU 时，显存容纳权重/KV 不代表计算、带宽和调度没有竞争；融合时更接近 `queue + max(agent A, agent B) + fusion/build + narrator + persistence`，不能把双 Agent 用时简单相加或仅靠 RTX 3090 Ti 显存容量解释。

### 8.2 历史测量与解释边界

受控真实 FusionService 样本曾得到整机 8.960 / 8.493 秒、同会话显卡追问 7.308 / 6.697 秒；解释路径样本约 1.44–1.79 秒。测量中，工具调用仅数毫秒，较大部分时间为模型生成；短 Narrator 约 0.7–1.1 秒，旧长润色曾约 4.2–5.3 秒并回退。

这些数据只能说明当时的受控代码路径存在明显的无效工作削减，不能与早期 50.547 秒 Job 总耗时做严格同负载 A/B：计时口径、候选、历史、Job 持久化、网络/SSE/前端渲染均不相同。它们更不是 P50/P95、并发容量或新版游戏门禁后的性能结论。新的验收必须在当前服务重启后、同一题集和统一计时口径下重新执行。

## 11. 用户系统：实施规划与当前复核

### 11.1 当前状态与安全原则

实施前 `UserConstraint` 仅是配置约束表。当前已加入 User、AuthSession、Conversation/Job.owner_id、登录/退出/改密撤销、登录弹层和角色路由、资源隔离与登录限流。独立刷新轮换、注册/任务限流、用户管理、持久审计及运维演练尚未完成。`/api/admin` 已受角色保护；本轮空白后台不等于完整管理系统。

用户体系继续作为**独立批次**推进；以下 U0–U4 是完整验收目标，不能因基础隔离已实现就整体勾选完成。不得为赶进度在请求体中接受自报 user ID，也不得把现有全部共享历史自动归给第一个注册用户。

### 11.2 目标边界与数据模型

建议的最小安全模型为：

| 对象 | 最小职责 | 关键约束 |
|---|---|---|
| `User` | 唯一身份、状态、创建/禁用信息 | 密码仅保存强哈希；不把邮箱/用户名作为授权凭据 |
| `UserRole` 或角色字段 | 普通用户与管理员权限 | 默认最小权限；管理员操作须审计 |
| `AuthSession` / refresh token | 设备会话、过期、撤销、轮换 | token 只存安全摘要；登出、改密、禁用可撤销 |
| `Conversation.owner_id` | 会话的服务端身份归属 | owner 仅由已验证身份写入；外键与 `(owner_id, updated_at)` 索引 |
| Job/Event/Message/Trace 的归属 | 经所属会话间接继承 | 任何直达 Job、SSE、trace、取消接口都必须重新授权，不能只信 UUID |
| 审计记录 | 管理操作、登录安全事件、关键删除 | 不记录密码、完整 token、Prompt/SQL 等不必要敏感信息 |

数据删除与保留策略需覆盖会话消息、上下文快照、任务结果、派生推荐参考、Agent 轨迹与审计数据；还需定义用户删除时正在运行 Job 的取消、保留或匿名化策略。

### 11.3 分批实施顺序

#### U0：设计与威胁建模

- 确定身份形态（本地账号优先，还是外部 SSO）与部署边界；未确定前不接入第三方登录。
- 制定匿名访问策略：禁止匿名、临时访客、还是明确只允许单机受控匿名；该选择决定旧会话迁移和路由行为。
- 列出全部资源入口：会话列表/详情/消息、创建/删除、约束、快照、Job 创建/读取/取消、SSE、trace、admin、下载/导出。每个入口写出资源归属检查和失败响应。
- 写出令牌寿命、刷新、撤销、CSRF/CORS、密码策略、限速、日志脱敏与备份恢复策略；安全选择需在实现前固定并形成接口契约。

#### U1：可回滚数据库迁移

1. 新增 User/角色/认证会话表与可空 `Conversation.owner_id`，不立即强制非空。
2. 对旧共享会话执行**预览**：显式认领、离线管理员分配或保持不可公开匿名状态三选一；不做自动归属猜测。
3. 备份、演练迁移、核对数量与外键后，再建立必要索引；满足归属政策后才决定是否收紧为非空。
4. 所有 migration 需要 downgrade/回滚说明、测试数据库演练与生产前备份；不与 Truth 数据发布混在同一批次。

#### U2：后端认证与授权中间件

- 实现注册/登录/登出/刷新/撤销/当前用户接口，统一从服务端认证上下文取得 actor。
- 建立资源级授权函数，而不是只给路由加“已登录”判断。会话、消息、约束、Job、SSE、trace、删除与管理员入口均复用它。
- 正在运行的请求需要明确策略：token 过期、撤销、用户切换后拒绝新的读写与 SSE 续连；是否取消已启动 Job 必须可观测且有产品定义。
- 对登录、注册、密码重置（如纳入范围）、Job 提交等入口按账号/IP 设速率限制；单 worker 阶段可先采用应用内可观测实现，不以引入 Redis/多进程为前提。

#### U3：前端身份隔离

- 添加登录、登出、会话恢复、权限导航和路由守卫；接口错误以用户可理解的方式显示，不泄露鉴权细节。
- 登录、退出、切换账号时关闭旧 EventSource/轮询，清空会话列表、详情、任务状态、推荐参考和本地缓存；localStorage 键必须按身份隔离或登出时清除。
- 明确定义“关闭页面/退出账号”与“取消服务器任务”的差别，提供显式取消入口，不让前端取消订阅被误解为服务器已停止。

#### U4：管理员与运维

- 管理员用户管理、禁用/恢复、必要审计查询与数据归属处置分权实现；开发统计接口不能直接暴露为生产管理端。
- 补充监控：认证失败、限速触发、越权拒绝、SSE 断开、任务取消、数据导出/删除；日志必须脱敏。
- 编写部署、备份、密钥轮换和事件响应说明。用户体系上线前先在隔离测试数据上演练恢复与撤销。

### 11.4 用户体系验收门槛

1. A/B 用户对会话、消息、约束、快照、任务、取消、SSE、trace、删除和任何直接 ID 路径交叉访问均被拒绝；UUID 难猜不是验收理由。
2. 匿名、过期、伪造、已撤销令牌和被禁用账户的所有入口都有测试；管理员与普通用户的权限边界可复现。
3. 同浏览器切换账号、多标签页、刷新、旧 SSE 迟到回调和运行中 Job 不得显示前一用户内容。
4. 旧数据迁移有备份、预览、数量核对、回滚和未归属数据的处理记录；不明确归属的数据默认不公开。
5. 完成 U0–U4 前，产品文案保持“开发/受控单用户使用”，不宣称已支持安全多用户共享。

### 11.5 本轮实施复核

原“均未开始”状态已失效。已修复首注册者自动提权、管理路由未检查角色、账号切换迟到响应等问题；公开注册始终为普通用户。指定管理员离线配置，后台位于 `/admin`。

## 12. 工程纪律、测试与回退

### 12.1 不可削弱的约束

- `TruthVerifier`、同实体 accepted Evidence 与 `no_supported_truth_claim` gate 不得以“提升成功率”为由放宽。
- NULL 永远是未知；规格、原始来源、估算、实测和推荐政策分层，估算不得覆盖实测。
- 改查询视图时，字段、`EVIDENCE_FIELD_BY_VIEW_COLUMN`、Prompt、DecisionContext、schema 与测试同步更新；只增视图列时注意 SQL 的位置映射风险。
- 数据导入顺序固定为审核、验证、dry-run、授权 apply；append-only 数据错写时精确回滚发布。
- 报告与界面不得把 completed、字段覆盖、模型自信或人工指数偷换为推荐质量、性能实测或兼容性证明。

### 12.2 已有验证与后续回归

本轮后端已完成 371 passed、6 skipped、0 failed；跳过项为无数据库凭据时按设计跳过的测试。新增/覆盖测试包括性能政策表面、时间恢复、Prompt/查询面语义、游戏配对门禁、类别覆盖、事实/证据错配、配置草案与回退等。后续每次改动至少运行受影响单元测试；涉及推荐、数据或 API 契约时运行全量后端回归，并在当前服务上增加真实题集验收。前端需恢复 unit、production build 和桌面/移动端浏览器验收，不能用模拟 API 替代真实 LLM 验收。

回退优先级：先停止推广并保留失败样本；数据用最新备份或 `rollback_release.py --release-key <key> --apply`；迁移按明确 revision downgrade；代码只针对已知路径做版本控制恢复。工作树目前存在用户既有未提交内容，禁止使用 `git reset --hard`、粗范围 restore 或 `git clean -fd` 作为“清理”。
