# 管理员工作区：实现范围与数据编辑评估

## 2026-09-18：按维护价值收敛后的编辑器（当前实现）

本次将原先“全量数据库编辑”的设想收敛为**日常数据维护**。以下范围取代下文第一阶段的“全部规格只读”描述；14–24 人日是全量关系、评测、发布与回滚平台的原始估计，不是这一收敛版本的工作量。

| 数据 | 当前维护方式 | 选择原因 |
| --- | --- | --- |
| 名称、生命周期、发布日期、推荐开关 | 沿用基础信息表单 | 纠正展示和上下架状态 |
| 别名 | 每行一个，新增、修改、移除，最多 100 个 | 解决简称、中文名、不同写法的识别问题；不要求规格证据 |
| CPU | 核心、线程、接口、基础功耗、基础/加速频率、核显、内存通道，共 8 项 | 直接影响兼容性和选型 |
| GPU | 显存容量、功耗、显存类型、带宽、位宽、PCIe 代际/通道、ECC，共 8 项 | 直接影响运行模型和电源选型 |
| 模型 | 总参数、激活参数、上下文长度、许可证，共 4 项 | 影响部署规模与使用限制；参数单位为“个”，非 B |
| 硬件报价 | 追加含币种、地区、新旧状态和北京时间的报价 | 价格会随时间变化，不能覆盖原始历史 |
| 实体 ID、归属关系、发布版本、评测成绩、派生排名、自动估算 | 只读 | 手动改写可能造成身份、来源和计算逻辑不一致 |
| 内存/存储/电源/平台及模型变体的结构化规格 | 当前只读，别名和硬件报价可维护 | 当前正式字段注册缺少相应可声明字段，先保留数据契约；不自动添加未经规划的字段 |

### 保存规则

- 新增 `GET/PATCH /api/admin/catalog/{id}/maintenance` 与 `POST /api/admin/catalog/{id}/quotes`，均使用服务端管理员权限。
- 服务端明确列出 20 个字段白名单，并核验本部署的 `field_definition` 为激活、可声明、对应正确原表列。客户端不能自定义字段或表名。每个实体只显示适用字段。
- 空值表示未知，不以 0 代替。数字按明确范围验证，整数不能带小数；验证线程与核心、基础/加速频率、总/激活参数之间的关系。缺失 CPU/GPU 规格行可随补充字段创建。
- 规格修改（含清空）必须填写来源标题、HTTP(S) 链接、原文摘录、修改原因并确认已核对。**系统不抓取链接，不把管理员填写的链接伪称为自动核验。** 保存形成管理员审核的 accepted 新证据。被替代的 accepted 旧证据状态改为 conflict，原文和值保留；清空字段不创建声称“值为零”的证据。
- 一次表单可修改多个字段，同一摘录须支持每个字段；不同来源的字段应分次提交。
- 所有修改、证据 ID、来源与前后值进入 `admin_change`。关键字段、别名、证据状态、近期报价和实体时间戳参与版本摘要，结合实体行锁防止陈旧表单覆盖；旧版本重复新增报价会返回 409。
- 价格仅限硬件、CNY/USD、CN/US/GLOBAL、全新/二手，金额需大于 0，采集时间不可为未来。历史价格不更新或删除，按现有 `price_latest` 及读取逻辑选择适用的最新报价。模型 API 按 Token 的计费不是硬件报价。
- 页面提供缺失项筛选、变更预览、来源表单、最近五条报价、最近十次修改记录，以及未保存离开确认。基础信息与关键数据草稿互斥编辑，避免两套表单持有不一致的版本。
- 不新增数据库表或迁移，复用 `0011` 和现有 Truth 表。**不自动发布或修改 release bundle，也未实现一键回滚。** 后续版本导入可能覆盖在线维护，修改记录用于核对。正式版本发布闭环仍是独立后续工作。

### 验证

在隔离 SQLite 数据库验证数据写入、缺失行补充、来源和旧证据状态、事务约束、范围与跨字段校验、外部修改冲突、权限、别名元数据保留、历史报价保留和重复提交保护；浏览器模拟 API 验证桌面/手机的维护操作。

真实库只读遍历 581 个目录实体，维护查询均可读取，20 类白名单字段在实体上合计出现 2464 项，其中 512 项为空。此检查没有修改实际硬件、模型、价格或来源记录。应用新接口仍需要后端加载最新代码；不会擅自执行上次待批准的服务重启。

## 本次交付

入口 `/admin`，左侧包含数据看板、用户管理、数据管理。当前模块保存在 `section` 查询参数中，刷新及浏览器前进/后退可恢复模块。所有新增 API 均经过服务端 `require_admin`，不能依靠隐藏前端入口绕过权限。

### 数据看板

- 独立 `token_usage` 表，统计网站请求在共享推理 HTTP 入口发起的调用，包括请求分析、聊天、Agent 各轮、压缩和解说。启动探测及脱离网站请求的脚本调用不计入。
- 保存模型名、供应商返回的输入/输出/总 Token、时间及记录来源，不保存提示词、密码或账户外键。账号、会话和任务删除不会减少累计用量。
- 全站累计与所选日期合计分别展示；按 `Asia/Shanghai` 的自然日绘制柱状图，无调用日期补零。最多查询连续 366 天；累计数不受日期筛选影响。
- **数值含义是已记录用量，而非可保证完整的供应商账单。** 未返回 usage、流中断、HTTP 失败等调用的用量保留为未知，统计未知调用次数；禁止按字符或流块数估算。写入故障记录服务端错误日志，不触发已完成推理的自动重试。
- 迁移从已有 `query_event.event_type = llm_completed` 导入历史数据，不重复累加 Agent 汇总或流式累计计数。旧版本未记录的分析、压缩、解说，以及已删除历史任务无法恢复。

### 用户管理

- 按用户名搜索、分页展示账号；不返回密码散列、登录令牌。
- 删除前必须输入用户名确认。管理员账号禁止删除；有排队、运行中或正在取消任务的账号暂不允许删除。
- 删除账号及登录会话，由现有迁移 `0010` 的外键级联删除会话、任务等关联数据。既有 `agent_run` 审计数据按原来的 SET NULL 规则保留，不承诺清除全部运行审计。
- 删除操作写入 `admin_change`，只保留执行者/对象 ID、角色及结果，不额外复制用户名。

### 数据管理第一阶段

- `truth.catalog_entity` 已有统一目录。`hardware`、`ai_model`、`model_variant` 都能映射成一行，因此**不需要把数据库重构成大宽表**。
- 列表覆盖全部实体，按硬件/模型过滤、按名称或稳定标识搜索、分页浏览，包含当前不可推荐记录。
- 详情可查看主表、各硬件规格表、模型/变体信息、别名、扩展属性、模型能力及价格历史；每个关联表最多展示 100 条并明确标示总数，避免一次加载整个数据库。这不是所有关系和证据的完整数据库浏览器。
- 可直接修改：名称、生命周期、发布日期、是否可推荐。修改原始 `catalog_entity` 记录，记录修改前后值；通过行锁和 `updated_at` 校验拒绝过时保存。稳定实体标识、类型和外键不允许修改。
- 规格、价格、证据及其他关联表目前只读。UI 明确展示这个边界，不能声称已经支持全部字段在线编辑。
- 保存修改不会修改已返回的历史推荐结果；之后读取原表的查询会看到新值。它也不会改写磁盘 release bundle，后续导入可能覆盖在线修改。

## 完整数据编辑：可行，但应分阶段

难点不在表格，而在保证修改后规格、扩展属性、来源证据、派生视图和发布包仍然一致。

推荐保留现有规范化数据库，采用“实体列表 → 分类详情表单 → 服务端事务 → 校验与审计”结构。不同硬件和模型表使用白名单字段映射，不能提供任意表/任意 SQL 写入接口。

以下是熟悉现有系统的一名开发者的粗略工程量，包含接口、交互与针对性测试，不含新数据采集；需要根据要开放的字段进一步收敛：

| 阶段 | 范围 | 预计增量 |
| --- | --- | --- |
| 规格编辑 | CPU/GPU/内存/平台/电源/存储、模型与变体分类表单；类型、单位、枚举、数值范围及跨字段校验；事务、冲突及审计 | 3–5 人日 |
| 多值与关系 | 扩展属性、别名、模型能力、兼容关系；引用选择器；新增/删除行；唯一性及外键处理 | 3–5 人日 |
| 来源与历史 | 价格快照、证据与来源、评测记录；正确的追加/修订语义；证据一致性验证 | 4–7 人日 |
| 发布闭环 | 草稿变更集、预览差异、验证后发布、导出/回写 bundle、冲突处理、回滚与视图核验 | 4–7 人日 |

完整版本约 **14–24 人日**，不是简单地给数据库套一张可编辑表格。若只维护少量 CPU/GPU/模型常用规格，可以显著收窄第一项；涉及可追溯来源的值仍应按现有证据规则处理。

当前第一阶段适合作为后续编辑器的基础。正式长期使用在线编辑前，建议完成发布闭环，避免数据库与版本化数据包发生持续偏离。

## 部署

本次新增 Alembic revision `0011_admin_workspace`，父版本为 `0010_user_accounts`。代码交付不自动对当前真实数据库执行迁移或删除/改写实际账号和目录数据。

在部署窗口停止旧进程，备份数据库，再在 `backend` 目录执行：

```powershell
..\.venv\Scripts\python.exe -m alembic upgrade head
```

然后启动新后端并部署前端构建。迁移会新增 `token_usage`、`admin_change` 并导入已有最终调用事件。先停旧进程是为了避免回填和新版本计量切换之间产生记录缺口。

测试使用内存 SQLite、模拟供应商及浏览器拦截 API；真实 PostgreSQL 权限、迁移执行和现有部署状态仍需在部署时核验。未调用真实推理端点。

### 2026-09-18 部署排查

### 请求耗时看板

`GET /api/admin/usage` 额外返回 `timing`：所选日期的有效样本数、平均响应秒数（创建至完成）、平均执行秒数（开始至完成）、平均启动等待秒数（创建至开始），以及补齐日期的逐日统计。沿用北京时间和同一日期筛选；按提交日归组，跨日完成的请求仍归提交日。平均值由 SQL 按请求加权计算，不对日均值再次取平均。

仅统计现存 `QueryJob` 中状态为 `completed`、三个时间字段完整且顺序有效的咨询请求。空样本返回 `null`，前端显示破折号，趋势不连空值。启动等待不包含执行过程中的模型调度；这些指标不代表首字延迟，也不覆盖硬件日报等非咨询任务。账号删除会级联删除耗时样本，但不会删除 Token 账本，因此两类统计覆盖范围不同。

无需新增数据库迁移；重新加载后端代码并更新前端构建即可生效。旧后端未返回 `timing` 时，前端保留 Token 展示并提示更新服务。验证：27 项内存数据库测试、前端构建、20 项管理员浏览器用例（其中两项修正定位器后重跑通过）；未调用实际模型服务。

### 原有服务路由排查记录

本机出现两个运行旧代码的 Uvicorn 监听进程：`127.0.0.1:8000` 与 `0.0.0.0:8000`。前端代理实际访问的 OpenAPI 未包含 `/api/admin/usage`、`/users`、`/catalog`，因此三页都返回 404。没有开启 `--reload` 的旧进程不会因为源文件修改而自动加载新路由。

真实数据库已从 `0010_user_accounts` 升级到 `0011_admin_workspace`。新增表存在，新版统计、用户、目录与详情查询已通过只读核验。旧进程仍需要重启；迁移与重启之间由旧版处理的调用不会自动补记到新用量表。

`backend/scripts/restart_backend.ps1` 可用于经批准的维护窗口：确认数据库版本和无活跃任务，核实所有监听进程确属当前仓库，停止旧进程，只启动一个单 worker 后端，再通过 OpenAPI 检查三个管理员接口。此脚本会短暂中断网站 API，不能在未经允许的情况下自动调用。
