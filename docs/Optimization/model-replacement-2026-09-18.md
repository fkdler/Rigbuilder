# “换一个”模型推荐去重

## 原因

“换一个”未被稳定识别为模型推荐的延续；已展示的模型没有进入检索排除条件。同一需求再次按相同规则排序，就会再次返回相同型号。提示模型不要重复，无法替代后端候选校验。

## 修改

- 识别“换一个／换一款／再推荐一个／还有别的吗”等有模型推荐上下文的请求，明确继续推荐模型。原用户要求中的用途、系列、资源和量化条件继续传递；显式不查数据库仍然优先。
- 任务提交时保存会话内的推荐引用快照，避免排队时读到变化后的另一轮答案。
- 在任务 JSON 中维护 `model_choice_state`，累计实际展示过的模型 ID；不会把未展示的候选也排除。连续替换累计排除 A、B，而不是在 A 和 B 之间轮换。
- 数据库检索先排除 ID 再排序和 LIMIT；模型的最终候选仍通过确定性校验，不能因事实正确就重新交付被排除的型号。
- 普通模型与视觉／语音等能力推荐入口共用排除上下文。能力推荐保存所展示的全部模型 ID，后续替换继续保留原能力要求。
- 只是换量化格式不会自动排除当前基座模型；解释推荐理由保留当前推荐链。明确开启新推荐需求时清空排除状态，聊天话题边界不沿用旧状态。
- 没有其他候选时明确说明候选不足，不循环推荐，也不放宽原条件凑答案。
- 排除状态使用请求局部 ContextVar，结束和异常均恢复，不影响并发会话；历史查询始终限定 conversation_id。无需迁移数据库表。

## 边界

旧的融合推荐记录可识别实际展示的 ID；旧记录没有累计状态时最多回看当前会话最近 50 个已完成任务，遇到新需求或话题边界停止。历史能力推荐如果只存了自由文本、没有模型 ID，无法可靠反推全部已展示型号；新返回的能力推荐已经保存 ID。

这些变化用于数据库推荐路径。显式禁用数据库时仍走普通问答，不宣称完成目录候选去重。模型同一基座的量化文件不会被当作一款新的基座模型；新任务中用户直接指定此前型号可以重新选择。
